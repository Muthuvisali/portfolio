01Problem & User
PM

Who the user is

Treasury and supply chain finance (SCF) operators at large enterprises — the people who decide, invoice by invoice, whether to pay a supplier on standard terms, push them into an SCF program, or pay early. Their manager is a CFO who needs the aggregate of those decisions to be fast, policy-compliant, and auditable on demand.

Why it matters now

This is grounded in a real deployment: Honeywell partnered with JPMorgan on a $900M+ SCF program across 260+ suppliers in 7 currencies. At that scale, three tensions show up every day:

  • Speed vs. compliance — manual review is slow and error-prone; static rule engines can't reason about nuanced supplier risk.
  • Autonomy vs. control — decisions need to move fast, but a high-risk call slipping through without policy validation is a real financial exposure.
  • Scale — thousands of invoices, each with a different supplier risk profile, currency, and contract term.

Job to be done

Turn an incoming invoice into a payment-term decision — in seconds, with a defensible reasoning trail — without the treasury team hand-reviewing every case.

02Product Decisions & Tradeoffs
PM primaryFDE secondary
Decision
Six narrow, single-purpose agents instead of one large "do everything" prompt.
Why / tradeoff
Traded implementation simplicity for auditability — in a compliance-sensitive domain, being able to point to exactly which agent produced which judgment (and at what confidence) matters more than a single elegant call.
Decision
A deterministic, rule-based governance layer sits on top of the LLM agents rather than trusting the model's own judgment end-to-end.
Why / tradeoff
Traded flexibility for defensibility. Hard IF/THEN policy rules (confidence >80%, risk/method alignment, escalation thresholds) are boring, inspectable, and easy to explain to a compliance reviewer — unlike "the model decided."
Decision
Confidence-gated auto-approval (>80% threshold) with explicit escalation triggers (>$5M or risk >75), instead of always auto-approving.
Why / tradeoff
Traded throughput for safety. Mirrors how real treasury escalation to a CFO actually works, so the automation earns trust incrementally rather than asking for blind faith.
Decision
Ship one fully worked case study (a $2.5M invoice) as the flagship demo, rather than building a large synthetic invoice dataset first.
Why / tradeoff
Traded statistical breadth for narrative clarity within a limited build window — the goal was to prove the reasoning pattern works end-to-end, not to establish population-level accuracy yet.

How quality is enforced

Each agent emits a per-output confidence score; the Governance Agent functions as an automated eval gate over the other five — checking confidence thresholds, policy/risk alignment, cross-agent contradictions, and field completeness before anything is marked approved.

Honest gap

Coverage is currently three scripted scenarios, not a benchmarked dataset. There's no adversarial/red-team invoice testing yet, no measured hallucination rate, and no LLM-as-judge scoring against a larger labeled set. Next step for production-grade eval: a held-out set of real (anonymized) invoices with human-labeled "correct" decisions to measure agreement rate.

04Architecture & Technical Stack
FDE primary

Pipeline shape

Invoice → Invoice Analysis → Supplier Risk → Working Capital Optimizer → Financing Recommender → Executive Summary → Governance Agent → Approved / Requires Review / Rejected / Escalate to CFO. Agents 1–5 are stateless with respect to each other — each reasons independently over the invoice and its own data slice using the ReAct pattern; only the Governance Agent sees all five outputs together.

Stack

  • Reasoning engine: Claude 3.5 Sonnet, one call per agent per invoice
  • Orchestration: LangChain (0.1.14) for agent tooling, LangGraph for the pipeline graph
  • Serving: Gradio (4.36.0) dashboard, deployed to Hugging Face Spaces (Docker-backed)
  • Runtime: Python 3.13
  • Data layer: supplier knowledge base (payment history, delivery metrics, financial health), treasury policy engine (rule thresholds), working-capital calculation models — currently in-memory / mock data, not a live ERP or treasury system feed

05Reusable Technical Assets
FDE primary

Prompt library

One ReAct-style prompt template per agent role, each deliberately scoped to a single, narrow judgment plus a confidence score — invoice validity, supplier risk, working-capital tradeoff, financing method, executive synthesis, governance check. The reusable pattern is "one agent, one narrow judgment, one confidence score" rather than one prompt trying to reason about everything at once.

Runbook: the governance rule table

IF amount > $5M → ESCALATE_TO_CFO
IF payment_method = "immediate" → ESCALATE_TO_CFO
IF risk > 75 AND method = "normal" → REJECTED
IF any agent confidence < 80% → REQUIRES_REVIEW
IF any policy check failed → REQUIRES_REVIEW
ELSE → APPROVED

This rule table is declarative and decoupled from the LLM agents — it's the one piece of the system that's meant to be edited by a compliance/treasury policy owner, not an engineer.

What I'd reuse as-is

  • The confidence-gated governance pattern — upstream agents reason freely; one deterministic downstream validator enforces hard constraints. This generalizes to any multi-agent system operating in a regulated or high-stakes domain (lending, healthcare triage, procurement).
  • The one-agent-one-judgment decomposition, as a default starting shape for any new agentic workflow.

What I'd change next time

  • Persist the audit trail durably (it's generated per run today, not stored) so "show me every decision from Q3" is answerable.
  • Replace the mock supplier knowledge base with a real data-ingestion adapter before touching any real invoice data.
06Deployment Readiness
FDE primary

Current state

Deployed to Hugging Face Spaces via Gradio on a free-tier Docker Space, which sleeps after inactivity and takes roughly 30–60 seconds to wake on the first request. Fine for a demo; not how it would run in production.

Not yet production-ready

  • No persistent database — audit trails and run history aren't stored durably.
  • No authentication or access control on the Gradio UI.
  • No integration with a real ERP/treasury system — invoice and supplier data are mocked.
  • Secrets managed via a local .env file only; no secrets manager.
  • No CI/CD — deploys are manual pushes to the Space.

Path to production

  • Swap the mock supplier knowledge base for a real data source / ERP adapter.
  • Add durable storage for the governance audit trail.
  • Add authentication and move off free-tier sleeping compute.
  • Add monitoring and alerting on governance escalations (an escalation is exactly the event a real CFO wants paged on).
